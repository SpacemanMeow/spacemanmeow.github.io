# Google Play SEO（ASO）规范

> **用途**：本仓库所有 Android 应用商店元数据的统一规范——关键词调研、名称 / 简短说明 / 完整说明撰写、合规审核与发布前校验。
> **适用范围**：Google Play 商店列表（store listing）及其**所有语言译文**；不覆盖站内网页 SEO 与 AI 搜索 SEO（边界见 §0）。
> **依据**：Google Play 官方《商店資訊最佳做法》与元数据政策（来源见 §2.1）；官方政策变更时以官方为准并同步修订本文。
> **最后更新**：2026-11-06
> **配套**：逐语言关键词证据、项目诊断、进度与实测结果放在各 App 描述目录的辅助工作记录中，不写入本文。

---

## 0. 文档边界

| 对象 | 归口文档 | 关注点 |
|---|---|---|
| Google Play 商店元数据 | **本文** | 名称 / 简短说明 / 完整说明、当地关键词、元数据合规、安装转化 |
| 站内网页 SEO | `SEO-PLAYBOOK.md` | 收录、URL、结构化数据、内链、内容集群、i18n、度量 |
| AI 搜索可见度 | `SEO-PLAYBOOK.md` §4 | 可抽取答案、实体一致性、被引用 |
| 站内关键词库 | `SEO-KEYWORDS.md` | 网站文章与落地页的词层、优先级、目标页映射 |

**不混用**：Play 商店文案对网页搜索排名与 AI 引用几乎不起作用；站内文章写法也不能直接套到商店三段文案上。Play Console 的搜索词数据可回填站内关键词库，但两套词库要分别维护。

## 1. 平台特性：为什么不能照搬网页 / AI 搜索 SEO

### 1.1 三者差异

| 维度 | 网页 SEO | AI 搜索 SEO（AEO/GEO） | Google Play ASO |
|---|---|---|---|
| 目标 | SERP 排名与点击 | 被大模型引用、进入答案 | 商店内被搜到并促成安装 |
| 索引对象 | 全网页面，可爬取 | 训练 / 检索语料与实体知识 | 商店内应用记录，封闭 |
| 可写内容 | 页面数量与篇幅几乎无限 | 网页 + 结构化数据 + 多源印证 | **仅 3 段文字且字数极紧** |
| 核心信号 | 外链权威、内容质量、技术 SEO、CTR | 实体一致性、答案可抽取、跨源印证、品牌提及 | 标题关键词、安装转化、评分、留存、卸载率、崩溃率 |
| 关键词堆砌后果 | 质量降权 | 可读性与可信度下降 | **违反元数据政策，可拒审 / 暂停应用** |
| 本地化 | hreflang、多语言页面 | 多语言实体一致性 | 每语言独立字段、独立索引、独立排名与转化 |
| 反馈工具 | Search Console / 日志 | 引用量、品牌提及监测 | 商店列表实验、Play Console 获客与留存数据 |
| 主要风险 | 算法更新 | 语料变化、引用被替代 | 元数据审核与下架 |

### 1.2 Play 独有机制

- **没有独立关键词字段**（不同于 iOS）：名称、简短说明、完整说明本身就是索引源，其中**名称权重最高**。
- **无外链、无爬取、无域名权威**，网页 SEO 的权威建设手段完全不适用。
- **行为质量信号参与排序**：安装转化率、评分、留存、卸载率、崩溃率属于产品侧优化，与文案同等重要。
- **本地化即增量**：每新增一个语言版本，等于新增一整套关键词空间与独立转化漏斗。

### 1.3 独有优化方向

1. 名称主词前置、品牌短名收尾；简短说明承接第二词簇；完整说明用自然句子铺长尾与功能事实。
2. 完整说明开头几行最关键：放主词 + 使用场景，不要复制简短说明原句。
3. 每语言按当地真实搜索词独立选词，**不互译**；截图、图标、宣传图同样本地化。
4. 用 Play Console「商店列表实验」分别测名称、简短说明、截图，按语言单独看安装转化率，不跨语言对比。
5. 只在功能真实上线后，才把对应长尾词写进描述。
6. 按语言定期复查当地在架标题，把新增的本地词补进内部关键词记录。

## 2. 官方规则与合规红线

### 2.1 依据与字符上限

- `https://support.google.com/googleplay/android-developer/answer/13393723`（商店資訊最佳做法）
- `https://support.google.com/googleplay/android-developer/answer/9898842`（元数据政策）
- `https://play.google.com/about/storelisting-promotional/metadata/`（元数据政策页）
- Play Console 帮助：字段字符上限

| 字段 | 官方上限 | **本仓库执行口径** |
|---|---|---|
| 应用名称 | 30 字符 | ≤ 30 |
| 简短说明 | 80 字符 | ≤ 80 |
| 完整说明 | 4000 字符 | **≤ 3000**（比官方更严，给后续迭代留冗余） |

全角与半角均按 1 字符计；校验用 Unicode 字符数（Python `len()`），不按字节或视觉宽度。

### 2.2 禁止项（官方要点）

1. 垃圾关键词、关键词堆砌、重复冗长或不相关的字块、非叙述性元数据；官方要求「以日常語言撰寫應用程式概覽，而非列出關鍵字」，违者可能暂停应用。
2. 排名 / 表现宣称：「年度應用程式」「第 1 名」「Play 精選」「熱門」「最佳」「評為第一」、获奖图标。
3. 价格与促销：「免費」「無廣告」（名称中）、折扣、限時免費、现金回赠；宣传描述不得提及价格或排名。
4. 未注明来源或匿名的用户评价；与其他应用作比较。
5. 误导性提述其他应用 / 产品 / 品牌、冒充、虚假暗示官方关系。
6. 名称中 emoji、特殊字符序列、全大写（品牌本身除外）。
7. 虚假或无法实现的功能陈述（欺诈行为政策）。
8. **不要在完整说明里重复简短说明的内容**。
9. 元数据政策适用于**所有商店资讯译文**，每个语言版本同样受审。
10. 描述简短直接、自然流畅、适合一般受众；不得含不雅用语；引用 / 推荐需注明来源。

### 2.3 常见违规模式（提交前逐项排除）

| 模式 | 问题 | 处理 |
|---|---|---|
| 逗号分隔的关键词词表（`key words: ...`） | 官方定义的「字块」 | 只作为内部记录存于文件顶部，提交时不复制 |
| HTML 标签（`<b>` 等）、异常符号 | 商店描述不支持 HTML，会原样显示 | 改纯文本 |
| 订阅价格、自动续订、iOS 支付流程（iTunes / Apple ID） | 价格信息 + 其他平台支付说明，Play 高风险 | 整段移除；订阅条款按 Play Console 正规流程配置 |
| 「立即下载」「还在等什么」等 CTA | 促销诱导 | 删除 |
| 简繁 / 字形 / 用语混用 | 本地化质量差，影响转化与审核 | 按目标市场字形与用语统一 |
| 机翻语法、主语错误 | 非叙述性元数据观感 | 由当地语言自然撰写，不互译 |
| 把会计术语当个人记账词、把 tracker 直译成本地词 | 不是当地真实搜索词 | 以当地在架标题为准纠正 |
| 写入当地高频但本应用不具备的功能 | 虚假功能陈述 | 功能未上线不入文案 |
| 竞品名、排名、「免费 / 最佳」 | 违规宣称 | 一律不写 |

> **功能真实性**：每个 App 单独维护一份「功能事实清单」，文案只能写清单内的功能；不得写「绝对安全 / 100% 加密 / 银行级」等无依据承诺，财务类应用也不得给收益或理财建议。

## 3. 关键词调研 SOP

> **硬规则**：每个语言用**当地语言**取证，禁止由英语或其他语言等价翻译生成关键词。

1. **确定目标市场**：语言代码 + 国家 / 地区代码（如 `ja`/`JP`、`pt_BR`/`BR`）；Play 不在运营的地区要选实际可检索的市场。
2. **Google Play 直接取证**：抓取当地商店搜索页
   `https://play.google.com/store/search?q=<当地语言候选词>&c=apps&hl=<lang>&gl=<country>`
   记录前 8–10 个在架应用标题，归纳反复出现的本地词；再用当地语言网站、评测文章交叉印证。
3. **分层**：`primary`（主词，进名称）/ `secondary`（第二词簇，进简短说明）/ `long-tail`（场景与功能词，自然织入完整说明）。
4. **记录**：检索式、在架标题证据、确认词、纠错说明（为什么原译法不成立）。证据写入项目辅助记录，不写进提交文案。
5. **复查**：每 4–6 周复查当地在架标题，新增词先补进内部记录，再决定是否织入正文。
6. **排除**：当地真实但本应用不具备的功能词，只能作为市场观察记录，禁止写入文案。

## 4. 三段文案规范

### 4.1 文件结构（内部记录 + 可提交正文）

```
# KEYWORDS (internal record — DO NOT paste into Play Console)
primary: ...
secondary: ...
long-tail: ...
evidence: ...

# TITLE (≤30)
...
# SHORT DESCRIPTION (≤80)
...
# FULL DESCRIPTION (≤3000)
...
```

- `# KEYWORDS` 区块置于**文件顶部**，供后续持续优化；标注为内部记录。
- 提交 Play Console 时**只复制三段正文**；整份文件粘贴会把关键词词表带进商店，直接构成堆砌违规。

### 4.2 各段写法

| 段落 | 写法 | 禁止 |
|---|---|---|
| 名称 TITLE | 本地主词 + 自有品牌，主词尽量前置；已在架的本地化品牌名沿用；不用 emoji / 全大写 / 特殊字符序列 | 同义词并列堆砌、无关修饰词 |
| 简短说明 SHORT | 一句自然的功能价值句，覆盖第二词簇；与完整说明首句不重复 | 词表、促销语、价格 |
| 完整说明 FULL | 首段主词 + 使用场景（含隐私 / 品牌差异化）；其后按「**吸引用户、最具差异化的特色功能 → 核心高频功能 → 通用 / 技术性功能 → 备份与数据保障**」排序，逐项列出功能事实清单里的真实功能，每项用自然句子写清细节，长尾词落在句子里 | 重复简短说明、列关键词表、堆同义词、不支持的 HTML、为精简把多项功能压成一句导致功能项缺失 |

- **排序原则**：商店列表首屏只显示开头几行，先把最能吸引目标用户、别家少见的特色功能（主题化设计、隐私保护、报销追踪、资产净值等）放在前面；通用功能与设置项放后面，备份与数据安全收尾。
- **功能完整性**：合规清理只针对 HTML 标签、emoji、价格订阅段、CTA、排名宣称与虚假功能；**功能本身不违规**，不得借合规之名删除功能细节，也不要把功能改写成关键词词表。3000 字上限足够容纳完整功能说明。
- **每语言独立撰写**，不互译；只写功能事实清单内的功能。
- 关键词**自然织入句子**，绝不列成词表。
- 不写价格、订阅价、续订流程、CTA、竞品比较、排名或「最佳 / 免费」宣称，不虚构功能。
- 完整说明保留字数余量，便于后续补长尾场景与做商店列表实验；字母语言逐项写全功能后容易逼近 3000，应压缩修饰语而不是删功能项。

## 5. 发布前校验

### 5.1 清单

- [ ] 每个语言文件含 `# KEYWORDS` / `# TITLE` / `# SHORT DESCRIPTION` / `# FULL DESCRIPTION` 四段
- [ ] 名称 ≤30、简短说明 ≤80、完整说明 ≤3000
- [ ] 简短说明与完整说明首句不重复
- [ ] 无订阅价格 / 自动续订 / iTunes / Apple ID / CTA / 排名宣称 / 竞品名 / HTML / emoji
- [ ] 关键词与证据一致，均来自当地检索，非跨语言直译
- [ ] 功能事实清单中的功能已逐项列出，没有因精简而丢失的功能项
- [ ] 特色功能与吸引用户的卖点排在完整说明前半部分
- [ ] 每个功能都可在功能事实清单中对应，无超前宣传
- [ ] 繁简与字形统一；目标语言无其他语言字符残留
- [ ] 只复制三段正文提交，内部关键词区块不入库

### 5.2 校验口径

- 按 `# TITLE` / `# SHORT DESCRIPTION` / `# FULL DESCRIPTION` 切分三段正文，用 Python `len()` 统计 Unicode 字符。
- 禁用词表基线覆盖：价格与金额、订阅 / 续订 / 跨平台支付、促销 CTA、排名与「最佳 / 免费 / 第 1」、竞品名、HTML 标签、emoji。
- 禁用词只在**三段正文**中检查；内部证据区允许出现在架应用标题作调研记录。
- 校验结果按语言列成表（标题 / 简短说明 / 完整说明字符数 + PASS/FAIL），记入项目辅助记录。

## 6. 持续运营

1. **商店列表实验**：分别测名称主词、简短说明句式、截图，按语言单独看安装转化率。
2. **定期复查词**：每 4–6 周复查当地在架标题与 Play Console 搜索词，增量更新内部关键词记录。
3. **Play Console 数据回填**：获客 → 商店列表 → 搜索关键字 / 来源，可用于站内关键词库（`SEO-KEYWORDS.md`）的月度维护。
4. **产品侧信号**：评分、留存、卸载率、崩溃率同样影响排序，文案之外需同步跟进。
5. **政策复核**：官方元数据政策更新时，先修订本文 §2，再回查全部在架语言版本。
