# Google Play SEO（ASO）规范

> **用途**：本仓库所有 Android 应用商店元数据的统一规范——关键词调研、名称 / 简短说明 / 完整说明撰写、合规审核与发布前校验。
> **适用范围**：Google Play 商店列表（store listing）及其**所有语言译文**；不覆盖站内网页 SEO 与 AI 搜索 SEO（边界见 §0）。
> **依据**：Google Play 官方《商店資訊最佳做法》与元数据政策（来源见 §2.1）；官方政策变更时以官方为准并同步修订本文。
> **最后更新**：2026-11-24
> **配套**：逐语言关键词证据见 `SEO-KEYWORDS.md`；实测字符数与发布校验在发布时按 §5 执行，项目进度见 `SEO-PROGRESS.md`。本文只保留可复用的 ASO 规范，不堆砌逐次执行流水。

---

## 0. 文档边界

| 对象 | 归口文档 | 关注点 |
|---|---|---|
| Google Play 商店元数据 | **本文** | 名称 / 简短说明 / 完整说明、当地关键词、元数据合规、安装转化 |
| 站内网页 SEO | `SEO-PLAYBOOK.md` | 收录、URL、结构化数据、内链、内容集群、i18n、度量 |
| AI 搜索可见度 | `SEO-PLAYBOOK.md` §4 | 可抽取答案、实体一致性、被引用 |
| 站内关键词库 | `SEO-KEYWORDS.md` | 网站文章与落地页的词层、优先级、目标页映射 |

**不混用**：Play 商店文案对网页搜索排名与 AI 引用几乎不起作用；站内文章写法也不能直接套到商店三段文案上。Play Console 的搜索词数据可回填站内关键词库，但两套词库要分别维护。

## 1. 平台特性：为什么不能照搬网页 / AI 搜索 SEO

### 1.1 三者差异

| 维度 | 网页 SEO | AI 搜索 SEO（AEO/GEO） | Google Play ASO |
|---|---|---|---|
| 目标 | SERP 排名与点击 | 被大模型引用、进入答案 | 商店内被搜到并促成安装 |
| 索引对象 | 全网页面，可爬取 | 训练 / 检索语料与实体知识 | 商店内应用记录，封闭 |
| 可写内容 | 页面数量与篇幅几乎无限 | 网页 + 结构化数据 + 多源印证 | **仅 3 段文字且字数极紧** |
| 核心信号 | 外链权威、内容质量、技术 SEO、CTR | 实体一致性、答案可抽取、跨源印证、品牌提及 | 标题关键词、安装转化、评分、留存、卸载率、崩溃率 |
| 关键词堆砌后果 | 质量降权 | 可读性与可信度下降 | **违反元数据政策，可拒审 / 暂停应用** |
| 本地化 | hreflang、多语言页面 | 多语言实体一致性 | 每语言独立字段、独立索引、独立排名与转化 |
| 反馈工具 | Search Console / 日志 | 引用量、品牌提及监测 | 商店列表实验、Play Console 获客与留存数据 |
| 主要风险 | 算法更新 | 语料变化、引用被替代 | 元数据审核与下架 |

### 1.2 Play 独有机制

- **没有独立关键词字段**（不同于 iOS）：名称、简短说明、完整说明本身就是索引源，其中**名称权重最高**。
- **无外链、无爬取、无域名权威**，网页 SEO 的权威建设手段完全不适用。
- **行为质量信号参与排序**：安装转化率、评分、留存、卸载率、崩溃率属于产品侧优化，与文案同等重要。
- **本地化即增量**：每新增一个语言版本，等于新增一整套关键词空间与独立转化漏斗。

### 1.3 独有优化方向

1. 名称主词前置、品牌短名收尾；简短说明承接第二词簇；完整说明用自然句子铺长尾与功能事实。
2. 完整说明开头几行最关键：放主词 + 使用场景，不要复制简短说明原句。
3. 每语言按当地真实搜索词独立选词，**不互译**；截图、图标、宣传图同样本地化。
4. 用 Play Console「商店列表实验」分别测名称、简短说明、截图，按语言单独看安装转化率，不跨语言对比。
5. 只在功能真实上线后，才把对应长尾词写进描述。
6. 按语言定期复查当地在架标题，把新增的本地词补进内部关键词记录。

## 2. 官方规则与合规红线

### 2.1 依据与字符上限

- `https://support.google.com/googleplay/android-developer/answer/13393723`（商店資訊最佳做法）
- `https://support.google.com/googleplay/android-developer/answer/9898842`（元数据政策）
- `https://play.google.com/about/storelisting-promotional/metadata/`（元数据政策页）
- Play Console 帮助：字段字符上限

| 字段 | 官方上限 | **本仓库执行口径** |
|---|---|---|
| 应用名称 | 30 字符 | ≤ 30 |
| 简短说明 | 80 字符 | ≤ 80 |
| 完整说明 | 4000 字符 | **≤ 3000**（比官方更严，给后续迭代留冗余） |

全角与半角均按 1 字符计；校验用 Unicode 字符数（Python `len()`），不按字节或视觉宽度。

### 2.2 禁止项（官方要点）

1. 垃圾关键词、关键词堆砌、重复冗长或不相关的字块、非叙述性元数据；官方要求「以日常語言撰寫應用程式概覽，而非列出關鍵字」，违者可能暂停应用。
2. 排名 / 表现宣称：「年度應用程式」「第 1 名」「Play 精選」「熱門」「最佳」「評為第一」、获奖图标。
3. 价格与促销：「免費」「無廣告」（名称中）、折扣、限時免費、现金回赠；宣传描述不得提及价格或排名。
4. 未注明来源或匿名的用户评价；与其他应用作比较。
5. 误导性提述其他应用 / 产品 / 品牌、冒充、虚假暗示官方关系。
6. 名称中 emoji、特殊字符序列、全大写（品牌本身除外）。
7. 虚假或无法实现的功能陈述（欺诈行为政策）。
8. **不要在完整说明里重复简短说明的内容**。
9. 元数据政策适用于**所有商店资讯译文**，每个语言版本同样受审。
10. 描述简短直接、自然流畅、适合一般受众；不得含不雅用语；引用 / 推荐需注明来源。

### 2.3 常见违规模式（提交前逐项排除）

| 模式 | 问题 | 处理 |
|---|---|---|
| 逗号分隔的关键词词表（`key words: ...`） | 官方定义的「字块」 | 只作为内部记录存于文件顶部，提交时不复制 |
| HTML 标签（`<b>` 等）、异常符号 | 商店描述不支持 HTML，会原样显示 | 改纯文本 |
| 订阅价格、自动续订、iOS 支付流程（iTunes / Apple ID） | 价格信息 + 其他平台支付说明，Play 高风险 | 整段移除；订阅条款按 Play Console 正规流程配置 |
| 「立即下载」「还在等什么」等 CTA | 促销诱导 | 删除 |
| 简繁 / 字形 / 用语混用 | 本地化质量差，影响转化与审核 | 按目标市场字形与用语统一 |
| 机翻语法、主语错误 | 非叙述性元数据观感 | 由当地语言自然撰写，不互译 |
| 把会计术语当个人记账词、把 tracker 直译成本地词 | 不是当地真实搜索词 | 以当地在架标题为准纠正 |
| 写入当地高频但本应用不具备的功能 | 虚假功能陈述 | 功能未上线不入文案 |
| 写入**已下线**的功能（如 CPU Monitor 的一键加速 / 垃圾清理 / 释放内存 / RAM Booster / Storage Cleaner，2026-11 已移除） | 虚假功能陈述 → 欺诈合规风险，比没上线更严重 | 从商店文案、关键词区、功能事实文件三处同步删除；只保留仍在的功能。注意区分"显示 / 监测占用"（真实）与"清理 / 释放 / 加速"（已下线） |
| 竞品名、排名、「免费 / 最佳」 | 违规宣称 | 一律不写 |

> **功能真实性**：文案只能写应用**实际具备**的功能，事实基准以各 `_apps/<slug>.md`、`_apps_<lang>/<slug>.md` 与 Google Play 在架描述为准（这些是已维护的功能事实来源，无需另建清单）；不得写「绝对安全 / 100% 加密 / 银行级」等无依据承诺，财务类应用也不得给收益或理财建议。

## 3. 关键词调研 SOP

> **硬规则 1**：每个语言用**当地语言**取证，禁止由英语或其他语言等价翻译生成关键词。
>
> **硬规则 2**：各市场用户的**用词频率不一样**，禁止把同一套语义骨架（如「Monitor + Temperature + CPU」）换词套到所有语言。功能词（GPU、频率、浮窗等）语义相同是产品事实，允许一致；但 `primary` 的主词和排序必须由**该市场在架标题的实际词频**决定。同一概念在某语言是主词、在另一语言可能只是长尾——按数据分，不按翻译对齐。

1. **确定目标市场**：语言代码 + 国家 / 地区代码（如 `ja`/`JP`、`pt_BR`/`BR`）；Play 不在运营的地区要选实际可检索的市场。
2. **Google Play 直接取证**：抓取当地商店搜索页
   `https://play.google.com/store/search?q=<当地语言候选词>&c=apps&hl=<lang>&gl=<country>`
   记录前 8–10 个在架应用标题，归纳反复出现的本地词；再用当地语言网站、评测文章交叉印证。
3. **数词频，定排序**：对前 10 个标题逐词计数，写出「词 → 出现次数」，按次数定 `primary` 的词序。**禁止跳过这一步直接照搬其他语言的主词顺序**。注意口径：标题词频是**开发者供给端**用词，不是用户搜索量；真正的搜索频率以 Play Console 搜索词报表为准，标题词频只是可用近似，两种数据冲突时以后者为准。
4. **分层**：`primary`（主词，进名称）/ `secondary`（第二词簇，进简短说明）/ `long-tail`（场景与功能词，自然织入完整说明）。
5. **记录**：检索式、在架标题证据、**词频计数表**、确认词、纠错说明（为什么原译法不成立）。证据写入项目辅助记录，不写进提交文案。
6. **复查**：每 4–6 周复查当地在架标题，新增词先补进内部记录，再决定是否织入正文。
7. **排除**：当地真实但本应用不具备的功能词，只能作为市场观察记录，禁止写入文案。

## 4. 三段文案规范

### 4.1 文件结构（内部记录 + 可提交正文）

```
# KEYWORDS (internal record — DO NOT paste into Play Console)
primary: ...
secondary: ...
long-tail: ...
evidence: ...

# TITLE (≤30)
...
# SHORT DESCRIPTION (≤80)
...
# FULL DESCRIPTION (≤3000)
...
```

- `# KEYWORDS` 区块置于**文件顶部**，供后续持续优化；标注为内部记录。
- 提交 Play Console 时**只复制三段正文**；整份文件粘贴会把关键词词表带进商店，直接构成堆砌违规。

### 4.2 各段写法

| 段落 | 写法 | 禁止 |
|---|---|---|
| 名称 TITLE | 本地主词 + 自有品牌，主词尽量前置；已在架的本地化品牌名沿用；不用 emoji / 全大写 / 特殊字符序列 | 同义词并列堆砌、无关修饰词 |
| 简短说明 SHORT | 一句自然的功能价值句，覆盖第二词簇；与完整说明首句不重复 | 词表、促销语、价格 |
| 完整说明 FULL | 首段主词 + 使用场景（含隐私 / 品牌差异化）；其后按「**吸引用户、最具差异化的特色功能 → 核心高频功能 → 通用 / 技术性功能 → 备份与数据保障**」排序，逐项列出功能事实清单里的真实功能，每项用自然句子写清细节，长尾词落在句子里 | 重复简短说明、列关键词表、堆同义词、不支持的 HTML、为精简把多项功能压成一句导致功能项缺失 |

- **排序原则**：商店列表首屏只显示开头几行，先把最能吸引目标用户、别家少见的特色功能（主题化设计、隐私保护、报销追踪、资产净值等）放在前面；通用功能与设置项放后面，备份与数据安全收尾。
- **功能完整性**：合规清理只针对 HTML 标签、emoji、价格订阅段、CTA、排名宣称与虚假功能；**功能本身不违规**，不得借合规之名删除功能细节，也不要把功能改写成关键词词表。3000 字上限足够容纳完整功能说明。
- **每语言独立撰写**，不互译；只写功能事实清单内的功能。
- 关键词**自然织入句子**，绝不列成词表。
- 不写价格、订阅价、续订流程、CTA、竞品比较、排名或「最佳 / 免费」宣称，不虚构功能。
- 完整说明保留字数余量，便于后续补长尾场景与做商店列表实验；字母语言逐项写全功能后容易逼近 3000，应压缩修饰语而不是删功能项。

### 4.3 多语文案生成规则（每语种必守）

> 这一节解决"翻译腔"和"地道度"。核心态度：**AI 必须对自己的语言产出负责，不得把地道度判断丢给用户，也不得以"建议找母语者过一遍"结案。** 用户没有母语者资源，AI 就是这道关本身。地道度不靠"读着顺不顺"这种主观感觉，靠下面两套可执行的约束——**当地在架语料对照** + **客观规则自检**。

#### 4.3.1 生成前：先取样，再动笔

每种语言写正文之前，必须先在 Google Play 抓 2–3 个**当地在架同类应用**的真实文案（标题 + 短描述 + 完整说明开头），作为句式和用词的样板。要求：

1. **取样来源分散**：不要只盯一个竞品。竞品本身可能是机翻或写得差（见 §4.3.4），多个来源取交集才稳。
2. **记录原文**：把抓到的当地句子原样存进内部 `evidence`，标 URL 和查询日期。这些是句式依据，不是要抄的内容。
3. **从样板提句式，不从中文/英文翻译**：先看清当地人怎么开头、怎么称呼用户（Sie/du、tú/usted、vous/tu 等）、怎么把功能写成句子，再按这个句式把自己应用的功能填进去。禁止把中文骨架逐句翻过去。
4. **术语对齐**：从在架语料里确认每个功能点的当地叫法（如"悬浮窗"在 es/fr/pt 用借词 Overlay、ja 用 オーバーレイ），一个概念全篇用一个词，不来回换。

#### 4.3.2 生成中：必须守的客观规则

这些是能验证的硬约束，逐条对照，不靠语感：

| 维度 | 规则 | 常见错误 |
|---|---|---|
| 语域一致 | 同一份文案内人称/敬卑必须统一：短描述和完整说明用同一套（全 Sie 或全 du、全 tú 或全 usted、全 vous 或全 tu、全敬体或全简体） | 短描述 `Überwachen Sie`（敬）、正文 `Erfahre ... du`（非敬），同一应用混用 |
| 冠词/介词 | 名词该带的冠词不能丢，介词支配的格要对 | es `por encima de juegos` 缺 `los`；`supervisa temperatura` 缺 `la` |
| 术语一致 | 同一概念全篇一个词，不混用本地词和借词 | pt 一处 `Overlay`、一处 `sobreposição` |
| 语法形态 | 性、数、格、变位、复数按目标语言规则，不套英语 | 俄语名词格错、德语 `zwischen` 后少冠词 |
| 完整成句 | 短描述和正文每项都要有谓语、能读成句子，不是词组罗列 | `实时查看CPU、GPU和电池温度、频率，悬浮窗显示`（一串名词词组） |
| 信息准确 | 功能范围按事实文件写，不扩大也不缩小 | "频率"并列在 GPU 后让人误读 GPU 也有频率；写 GPU 使用率但应用只有温度 |
| 字形用语 | 简繁分开、地区用词分开，不混用 | zh-tw 写 `記憶體占用`（应为 `佔用`）；台湾用简体取证词 |
| 字符上限 | 标题 ≤30、短描述 ≤80、完整说明 ≤3000 | 为塞卖点超 80 |

#### 4.3.3 生成后：逐项校验并表格输出（强制，不可省略）

**每次文案生成或修改后，必须对每一项做校验，并在对话窗口以表格形式输出核对结果。** 只说"已完成""全部 PASS"不算交付。表格至少包含下列每一项，逐项写 PASS/FAIL 和依据：

| 校验项 | 怎么验 | 输出要求 |
|---|---|---|
| 字数 | 按 §5.2 切三段，Python `len()` 统计 | 三个语种字符数 + 是否达标，逐语种列 |
| 语域一致 | 搜全文人称词（du/Sie、tú/usted、tu/vous、敬体/简体），确认只有一套 | 列各语种采用的语域 + 有无混用 |
| 术语一致 | 对同一概念搜所有叫法，确认只有一个 | 列功能点的选定词 + 有无异写 |
| 冠词/介词/语法 | 按 §4.3.2 逐条对照取样语料 | 列出发现并修正的问题，没有就写"无" |
| 完整成句 | 逐句看有无谓语、是否词组罗列 | 列有问题的句子 + 改后 |
| 信息准确 | 逐功能对事实文件 `_apps*/<slug>.md` | 列功能项覆盖情况 + 无误写 |
| 关键词覆盖 | 对照内部 KEYWORDS 区和 §3 取证词 | 列覆盖/未覆盖的词 |
| 地道度对照 | 每语种至少 1 句与在架语料句式比对 | 列参照的在架原句 + 本应用对应句 |
| 合规红线 | 按 §2.2 / §2.3 逐项排除 | 列已排除项，确认无违规 |
| 简繁/字形 | 简繁、地区用词检查 | zh-cn/zh-tw 分别确认 |

校验表必须说明每一项"符合 / 不符合 + 依据"，不允许只打勾。发现 FAIL 先修再交付；**确实无法独立判定的地道度取舍，按 §4.3.4 自己决策，不得抛给用户**。

#### 4.3.4 地道度取舍：AI 自己决策，不外抛

取样语料和客观规则对同一处给出两种写法时（例如当地既说 GPU 也说 carte graphique、既说 Sie 也说 du），按下面的优先级**自己定**，并把决策和理由写进校验表：

1. **关键词覆盖优先**：涉及要吃的搜索词（如 GPU temperature），保住关键词，用自然句子把它织进去，不为"更地道"丢掉主词。
2. **语域统一优先于单句好看**：一处想用 du 但全篇是 Sie，就统一到 Sie；反过来也一样。宁可全篇稳，不要一句俏。
3. **在架多数优先**：多个来源里多数用的写法胜出，少数写法除非更契合本应用定位否则不用。
4. **事实文件为准**：任何写法不得超出应用实际功能，地道和功能真实性冲突时，功能真实性胜。

决策记进校验表的"地道度对照"行，格式：`取舍点 → 选定写法 → 依据（哪条优先级 + 哪个在架来源）`。**禁止出现"建议找母语者确认""交给你定"这类表述。**
